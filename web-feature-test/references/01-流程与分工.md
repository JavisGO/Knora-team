# 01 流程与分工

本流程由“人 + 工具”组成，**不依赖某一个 AI agent**。文中的“执行者”可以是测试同事本人、也可以是任何能运行命令行并读写文件的 AI agent；“主测”是对结果负责、做核对和汇报的人（或 agent）。

## 总览：8 个阶段

| 阶段 | 谁做 | 产出 | 通过标准 |
|---|---|---|---|
| 0 接单确认 | 主测 + 需求方 | 填好的《测试需求输入单》 | 被测对象、环境、账号、需求原文、范围边界齐全 |
| 1 需求拆解与用例设计 | 主测 | 测试计划（含需求→用例追溯） | 每条需求至少一个用例；写不出用例的条款标“待澄清” |
| 2 预检与登录 | 执行者 | `wft doctor` 通过；登录态文件 | 环境可达、浏览器可启动、已登录 |
| 3 造数 | 执行者 | 数据包 + manifest | 正常包与异常包齐全，期望结果有记录 |
| 4 写用例并执行 | 执行者 | `spec.json`、`results.json`、截图、trace | 冒烟先过；每个用例有结果和截图 |
| 5 判定与成文 | 主测 | 测试报告（含缺陷清单、结论） | 待人工判定项都已看图定论 |
| 6 核对与交付 | 主测 | `wft check` 通过的交付目录 | 无 ERROR；关键截图人工抽查 |
| 7 复测/补测 | 执行者 | 补测报告并入终版 | 缺陷修复后按原用例回归，旧报告保留为历史 |

## 阶段 0：接单确认

必须问清（缺哪项问哪项，不要自己猜）：
1. **被测对象是哪一个**——以需求方指定为准，不得因为“结构简单”“跑得快”自行更换。
2. **环境和账号**，以及**是否有别人/别的自动化同时在用同一个环境和账号**。
3. 允许造什么数据、能不能改共享配置（默认不能）、**怎么造出一条会失败的数据**（失败项相关用例需要）。
4. 交付形态（默认：每个被测对象一份报告，每个测试点带截图，只保留自测内容）。

## 阶段 2：预检、登录与冒烟

```bash
python -m wft doctor --url <被测地址> --out <输出目录>
python -m wft login  --url <被测地址> --account <账号> --state <登录态文件>   # 口令走环境变量或交互输入
```

冒烟原则：用最小数据（1 用例 × 1 轮）走一遍主链路，用例里标 `"smoke": true`。
- 通过：继续其余用例。
- 失败：`wft run` 会自动停止后续用例，并留下现场截图与接口响应。**最多再试 2 次**，仍失败就写“主链路阻塞”报告，不要堆几十次重试，更不要把后面的用例写成通过。
- 需求方说“已修复”后，从冒烟重新开始，不凭一句话默认修好。

## 阶段 4：并行还是串行

平台通常不支持同一个浏览器里同时登录（后登录的覆盖先登录的），这是正常行为。因此：

| 条件 | 做法 |
|---|---|
| 每个执行者各用一次独立的 `wft run`（每次运行都是独立的浏览器上下文，各带一份登录态文件） | 可以并行；账号相同或不同都行；每人独立的输出目录、任务名前缀 |
| 执行者共用同一个**手动操作的浏览器**（如大家都在同一个 Chrome 里点） | 不能并行，串行 |
| 同一个账号、同一个环境里还有别的自动化或同事在用 | 视为并发会话：任务名前缀区分归属，筛选类断言逐行核对，不靠总数 |
| 被测对象之间有数据依赖 | 串行 |

并行时必须隔离的三样：**输出目录、任务名前缀、截图文件名前缀**。`wft init` 会生成这些约定写进 `run.json`。

## 谁来执行：三种方式

1. **纯人工 + 命令行**：测试同事自己写 `spec.json`，`wft run`，看结果，写报告。
2. **AI agent 辅助**（Claude Code、Codex、Cursor 等任何能执行命令的 agent）：把 `SKILL.md`/`AGENTS.md` 交给 agent，让它按流程写用例、跑 `wft run`、看截图、写报告。agent 平台支持子任务/子智能体时，可以把“一个被测对象一轮测试”交给一个子任务，用 `templates/测试员提示词模板.md`。
3. **定时回归**：把已验证的 `spec.json` 放进 CI 或计划任务，`wft run … --priority P0` 定时跑，失败就通知。

执行者分工建议：一个执行者负责一个被测对象的一轮测试；单个 agent 的一次会话建议不超过约 150 次工具调用，超出就拆成“主测 + 补测”，并**每完成 3 个测试点落盘一次**（`wft run` 本身每次都会写 `results.json`）。

## 阶段 5：判定与成文

- `wft run` 的结果是“通过/失败/阻塞/未测”，其中“未测（待人工判定）”是需要人看截图后定论的项（有 `manual` 步骤或没有任何断言）。
- 用 `python -m wft report out/results.json` 生成“用例明细”表，粘进报告；缺陷清单、未覆盖项、结论由人写。
- 按 `02-测试规范.md` 的口径判定；需求明确禁止的行为不能因为“能用”判通过。

## 阶段 6：核对（主测不能省）

1. `python -m wft check <报告> --run run.json`，ERROR 必须清零。
2. 人工抽查：
   - **所有“致命/严重”缺陷的截图**逐张看，确认截图确实显示了报告写的现象。
   - 每份报告至少抽 3 张“通过”用例的截图，确认没有张冠李戴。
   - 关键数字（计数、Token、耗时）回到截图/原文核对。
3. 复核缺陷判定：容易把“需求明确禁止的行为”判成通过、把“没找到入口”判成缺失，按 `02-测试规范.md` 纠正。
4. 清点证据归属：新建任务名称是否都带本轮前缀；有无引用他人的截图/任务；有无他人文件混进来。
5. 汇总计数以明细为准，重新数一遍再汇报。

## 阶段 6：整理交付

```bash
python -m wft deliver --report <终稿.md> --src <工作目录> [--src <补测目录>] \
    --out <交付目录>/<对象名> --testdata <数据包目录>
python -m wft check <交付目录>/<对象名>/测试报告.md
```

- 交付目录只含：终版报告、被引用的截图、测试数据；中间稿、他人产物不进交付目录。
- 不删除源文件。要清理中间产物，先列清单给需求方确认。
- 修复前后的报告：终版放 `测试报告.md`，修复前的另存为 `历史-<说明>.md` 并随包附上。
- **清理测试数据**：本轮创建的数据（带前缀的任务）在交付时列清单给需求方，由需求方决定是否删除；未带前缀的误建数据要明确告知。

## 阶段 7：复测/补测

- 触发：缺陷修复、环境恢复、需求方要求补测。
- 做法：新开一轮（`wft init --round N`），截图前缀 `R{N}_`，不覆盖上一轮；只重做相关用例，加上必要的回归；结论里写清“哪些缺陷已验证修复、哪些仍存在、哪些是新发现”。
- 终版报告把各轮合并成一份，历史报告保留。
