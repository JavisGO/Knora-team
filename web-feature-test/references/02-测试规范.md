# 02 测试规范

## 1. 命名与标识

| 对象 | 规则 | 例 |
|---|---|---|
| 用例编号 | `TC-两位数字`，补测另起 `S/B/A + 数字` 须在报告里说明对应关系 | TC-12 |
| 缺陷编号 | `D-两位数字`，一份报告内唯一；复测沿用旧编号并标注“仍存在/已修复” | D-03 |
| 登录态文件 | `state-{账号}.json`（放在 skill 目录之外，权限 600） | ~/.web-feature-test/state-alice.json |
| 测试任务名前缀 | `【自动化测试-{对象}R{轮次}】` | 【自动化测试-订单导入R3】B0冒烟 |
| 截图 | `R{轮次}_{用例编号}_{描述}.png`，只用字母数字中文下划线 | R3_TC-12_轮次0失焦变1.png |
| 数据包 | 用途 + 规模，保留 manifest | R2_A1_3cases.zip |
| 报告 | 每个被测对象一份 `测试报告.md` | |

任务名称前缀是“证据归属”的依据：列表里混有别人的任务时，靠它区分哪些是自己的。

## 2. 结果判定口径

| 结果 | 判定 |
|---|---|
| 通过 | 预期全部满足，并且有截图证据 |
| 部分通过 | 主要预期满足，但有缺项；缺项要具体写出（如“字段齐全，行值未验证”） |
| 失败 | 实际与需求不符，或需求明确禁止/要求的行为未满足 |
| 阻塞 | 前置条件不满足，无法执行（如任务创建失败），要指明阻塞它的缺陷编号 |
| 未测 | 主动不测（安全边界、需修改共享配置、环境不具备），要写原因 |

判定原则：

1. **需求原文优先**。需求写了“不静默替换数据”“校验失败要给出具体位置和原因”，就以此为判据。“能用”“有兜底”不等于通过。
2. **没测到不能写通过**。抓不到的瞬时状态、没造出的失败数据，写“未测/未能验证”并写清尝试过程。
3. **需求没写的，不判失败**，写“需求未明确”，如实记录实际行为，交给产品确认。
4. **“没找到”不等于“没有”**。入口/按钮/菜单找不到时，先排除：标签页在后台、下拉未展开、权限、渲染延迟、被顶下线；至少用两种方式确认；仍不能确认写“待复核”。
5. **会话被顶下线期间的异常**（点击全部失效、列表为空）不能直接定为产品缺陷，标“待复核”，在单人环境复测。
6. **成功/失败只表示执行是否完成**这类口径题，按需求原文逐条核对，不要自己延伸。
7. 同一问题在不同对象上复现，各自记录，在缺陷里写“与 X 报告 D-xx 同源”。

## 3. 缺陷严重程度

| 级别 | 标准 | 例 |
|---|---|---|
| 致命 | 主链路不可用，阻断大多数用例 | 创建任务一律 500 |
| 严重 | 核心功能结果错误，或数据/隔离被破坏，结论不可信 | 执行之间上下文泄漏 |
| 一般 | 与需求不符但有变通，或重要信息缺失 | 详情缺配置快照；状态口径与需求不符 |
| 轻微 | 文案、体验、一致性问题 | 空值符号不统一；提示文案误导 |

“待复核”可以写在级别后面，如“严重（待复核）”。复核后改定级，不要留悬空。

每个缺陷必须有：编号与一句话标题、严重程度、复现步骤（别人能照做）、实际（含原文提示/接口返回）、期望（对应需求条款）、影响、截图。

## 4. 证据要求

- 每个测试点（含失败、阻塞、各类校验报错）都截图，并在报告中用 Markdown 图片语法嵌入，路径相对报告文件。
- 无法截图的写“无截图：原因”，不留空。
- 提示文案、数字、接口返回，直接摘录原文，不转述。
- 接口类证据：请求路径、HTTP 状态、响应体、时间。口令/令牌打码。
- 截图要能证明结论：失败用例的截图必须显示出错现象本身，而不是进入页面前的画面。
- 报告里不写口令、令牌、内网凭据。

## 5. 禁止项

1. 修改、删除已有的共享配置或他人数据。
2. 点开、引用、重跑他人创建的任务；把他人的截图/文件当成自己的证据。
3. 用 curl 等绕过界面去“测试”前端功能（接口抓取取证除外）。
4. 把没测到的写成通过；把环境问题写成产品缺陷而不加“待复核”。
5. 失败后无上限重试；冒烟失败最多再试 2 次。
6. 自行更换用户指定的被测对象。
7. 在报告、脚本、提示词里写口令。

## 6. 验证“上下文隔离/不继承”这类行为的方法

- 用两个用例×多轮：用例 A 告诉系统一个独特暗号（如“示例暗号X7”），用例 B 追问；再单用例多轮追问“上一轮我说过什么”。
- 逐轮记录**输出原文**和会话 ID；判定看“有没有任何一轮答出暗号”，不能只看会话 ID 不同。
- 泄漏可能是时序相关的，所以要多轮重复，并在报告里写明复现比例。

## 7. 报告写作规则

- 结论先行：第一屏就能看到“能不能验收、最严重的问题是什么”。
- 计数必须和明细一致（脚本会核）；失败、阻塞、未测要逐条点名。
- 避免“不是……而是……”式对比句和机械排比，用自然、直接的陈述。
- 面向业务和测试同事阅读：用业务语言写现象与影响，技术细节（接口路径、响应体）放在缺陷证据里。
