# 03 验收标准

分两层：**功能验收**（被测功能能不能上线/交付）和**测试交付验收**（这份测试报告合不合格）。

## A. 功能验收

### 验收结论的四种取值

| 结论 | 条件 |
|---|---|
| 通过 | P0、P1 全部通过；无未关闭的致命/严重缺陷；阻塞=0；未测项都有书面豁免 |
| 有条件通过 | P0 全部通过；无致命/严重缺陷；仍有一般/轻微缺陷或个别 P1/P2 未测，并列出整改清单与时限 |
| 不通过 | 任一 P0 失败；或存在未关闭的致命/严重缺陷 |
| 无法验收 | 主链路阻塞（创建/运行不可用），大部分用例无法执行。此时不给“通过/不通过”，只给阻塞原因和修复后的补测计划 |

默认判据（项目有自己的标准时以项目为准，并写在测试计划里）：

- P0：主链路与需求的核心承诺。例：创建→运行→看结果能走通；统计口径正确；隔离性成立；数据不丢。
- P1：规则与校验。例：必填/类型/边界校验给出可定位的原因；筛选/搜索结果正确；重跑规则。
- P2：体验与一致性。例：文案、占位符、提示是否清晰。
- “待复核”的缺陷在复核前按其严重程度保守计入。
- 未测项：只有“按安全边界主动不测”和“环境不具备”可以豁免，需写明原因并由用户确认；“没时间/没做到”不能豁免。

### 缺陷关闭条件

缺陷只有在**同一复现步骤复测通过并留有截图**时才能关闭；报告里写“已修复（R2 复测，截图见…）”。

## B. 测试交付验收（报告合格线）

交付前逐项过一遍，其中带 ★ 的由 `wft check` 自动核对。

| # | 检查项 | 自动 |
|---|---|---|
| 1 | 报告含：概述、结果汇总、用例明细、缺陷清单、未覆盖项、结论、本测试员新建的任务 | ★ |
| 2 | 每个测试点有结果；失败/阻塞/未测都写了原因 | ★（失败必须有截图或“无截图：原因”） |
| 3 | 汇总计数与明细一致 | ★ |
| 4 | 所有引用的截图存在、非空、是真实图片 | ★ |
| 5 | 每条缺陷带截图（或写明无法截图的原因） | ★ |
| 6 | 存在失败/阻塞/未测时，结论没有“全部通过/可验收”等表述 | ★ |
| 7 | 新建任务名称都带本轮前缀 | ★（警告） |
| 8 | 没有口令等敏感信息 | ★（警告） |
| 9 | 没有把他人产物当证据（边界声明除外） | ★（警告，需人工确认） |
| 10 | 致命/严重缺陷的截图已由主 agent 逐张查看，与文字一致 | 人工 |
| 11 | 至少抽查 3 张“通过”截图，内容与结论吻合 | 人工 |
| 12 | 缺陷定级符合 `02-测试规范.md` 的口径；需求明确禁止的行为没有被判通过 | 人工 |
| 13 | “没找到入口/按钮”类缺陷已排除前台/渲染问题 | 人工 |
| 14 | 结论第一屏就能看出能否验收、最严重问题是什么 | 人工 |
| 15 | 交付目录只含终版报告、被引用截图、测试数据；历史报告单独命名 | 人工 |

## C. 对用户的汇报格式

1. 一句话结论（通过/有条件通过/不通过/无法验收 + 最严重的问题）。
2. 计数表（通过/失败/阻塞/未测/合计）。
3. 缺陷清单（编号 + 一句话 + 严重程度）。
4. 未测项与原因。
5. 关键限制（环境干扰、并发会话、哪些结论待复核）。
6. 下一步（需要用户做什么/建议怎么补测）。

不要凭印象报数字，数字从明细重新统计。
