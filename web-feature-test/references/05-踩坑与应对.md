# 05 踩坑与应对（来自真实的多执行者并行测试，已按 Playwright 版整理）

## 1. 协作与并行

| 坑 | 后果 | 应对 |
|---|---|---|
| 多个执行者共用同一个手动操作的浏览器并行 | 平台不支持同一浏览器同时登录，后登录覆盖先登录，表现为列表变空、点击无响应、被带到登录页，一批用例只能标“待复核” | 每次 `wft run` 都是独立的浏览器上下文，各带登录态文件，可以并行；共用手动浏览器的只能串行 |
| 同账号在同一环境里还有别的自动化/同事在用 | 列表里混入他人数据，筛选计数被干扰，报告误把他人数据当成自己的证据 | 任务名前缀区分归属；筛选类用例逐行核对；整理交付时只拷“报告引用的图片” |
| 执行者自行更换被测对象 | 测的不是需求方要的 | 提示词里写明“需求方指定，不得自行更换” |
| 单个 agent 会话任务太大 | 上下文超限（约 100 万 token）后被强制终止，报告没写完 | 建议每会话 ≤ 约 150 次工具调用；拆成主测+补测；`wft run` 每次都落盘 `results.json` |
| 网关 502 / API 400 打断 agent | 任务中途失败 | 先看输出目录已落盘内容，从未完成的用例接着跑（`--only`）；同类错误反复出现就换新会话 |
| 主测自己重复做执行者在做的事 | 同账号冲突、浪费 | 派发后等结果，不重复操作 |

## 2. 判定偏差（主测复核时重点看）

1. **把“需求明确禁止”的行为判成通过**。例：输入非法值被静默修正，执行者写“有兜底，通过”。需求要求“给出原因、不静默替换”，应判失败。
2. **把“没找到”判成“没有”**。例：卡片上没看到入口，实际是“更多”下拉没渲染出来（后台标签页的动画停在“进入准备”态），切到前台就有。看现场截图和 trace 再下结论。
3. **把环境干扰判成产品缺陷**。被顶下线期间的“点击无效”要标“待复核”；页面一直转圈、`ERR_NETWORK_CHANGED` 这类先看环境。
4. **选中即生效 vs 需点查询**。“筛选不生效”实际常是要再点“查询”。先复现、再下结论，缺陷标题写准确。
5. **用例预期写得比需求更死**。例：断言“第 2 行”，系统按 Excel 实际行号报“第 3 行”（表头算第 1 行）。用例写成“第 N 行 + 列名”，行号口径另记一条说明。
6. **对象之间口径不一致**。同一问题在两份报告里一份判通过一份判失败，整理时统一口径。

## 3. 自动化本身的坑（`wft` 已处理的，和你写用例时要小心的）

| 坑 | 说明 | 处理 |
|---|---|---|
| 定位到了页面上另一个同类控件 | 弹窗叠在列表之上，页面里第一个文本框是列表的搜索框，“清空任务名称”其实清的是搜索框，正常数据被提交，**真的创建了数据** | 定位用 `after_text`/`within`，不要用页面级 `nth:0`；`wft run` 的数据创建护栏会在这种情况下判失败并停止 |
| 异常数据包被系统当成正常数据 | “必填缺失”包里，第 2 行其余单元格也是空，整行成了“全空行”被忽略，剩下 1 条有效数据被创建 | `wft pack` 造数时保证该行其余单元格有内容 |
| 步骤描述字段 `label` 与定位字段撞名 | 带描述的步骤去找一个叫该描述的表单标签，悬停超时 | 定位字段改名 `by_label`；`label` 只做描述 |
| 登录脚本抢跑 | 单页应用先加载目标页再跳登录页，脚本误判“已登录”，保存了无效登录态 | `wft login` 先等登录框出现；仍停在登录页则报错 |
| 读不到接口响应体 | 请求体是直接用文件作为请求体（不是表单 multipart）时，Chrome 会回收响应体，监听报 “Request content was evicted from inspector”，`expect_response` 的 `body_contains` 无法判断 | `wft run` 会在明细里提示“响应体读不到”；改用页面提示断言，或只断言状态码；真实系统多用表单上传，通常不受影响 |
| 内网瞬断 | `net::ERR_NETWORK_CHANGED`，用例被判阻塞 | `goto` 自动重试 3 次；卡片等待放宽到 45 秒 |
| 瞬时状态抓不到 | 任务秒级完成，看不到“执行中/待执行” | 加大用例数×轮次，创建后立即读取；仍抓不到写“未捕捉到” |

## 4. 数据与环境

- **主链路冒烟失败**：同一操作换多种合法数据包都失败，基本是服务端问题。取证（请求路径、状态码、响应体、时间）后交给开发，不要继续堆重试。需求方说“已修复”后，重新冒烟，不凭一句话默认修好。
- **“列表为空”**不一定是筛选问题，可能是数据没落库；先看创建动作是否真的成功（`expect_response`）。
- **没造出失败数据**：无效附件、超长文本这类常见手段执行都成功了。失败项相关用例（失败状态、失败 Token、失败重跑）如实写“未能构造失败项”，并向需求方/开发要“怎么能造出失败”（如临时让某个节点报错），不要硬写通过。
- **同一功能有两类对象**（例如流程与智能体）：各出一份报告，每份都有自己的任务、截图和结论；共性问题互相引用编号。
- **测试数据清理**：谁创建谁登记。交付时列出本轮创建的数据，由需求方决定是否删除；误建的（没带前缀的）要明确告知。

## 5. 报告质量

- 汇总数字与明细曾经差 1（笔误），是 `wft check` 核出来的。**交付前必跑，数字从明细重数**。
- 有的报告里某个测试点没有截图（只写了文字）。提示词里写死“每个测试点截图”，并用 `wft check` 检查。
- 截图文件名要有前缀和编号，否则多轮并存时分不清是哪一轮拍的（`--prefix R1_`）。
- 交付目录保留“历史报告”并清楚命名，终版报告里注明与历史版的关系，避免拿错版本。

## 6. 与需求方沟通

- 开始时说清：谁测什么、产物放哪。
- 中途失败要直说原因和影响，别让人等一个不会来的结果。
- 说“修好了”但实测仍失败：给出证据（时间、请求、响应），建议看服务端对应时间点的日志，不要争论。
- 汇报的数字、结论一律以明细为准，宁可晚一点报，不要报错。
