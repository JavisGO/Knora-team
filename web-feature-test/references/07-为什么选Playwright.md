# 07 为什么选 Playwright（选型记录）

本 skill 最初用 opencli（借助本人 Chrome 登录态的命令行浏览器工具）完成了第一次真实测试，随后评估并在真实环境试跑了 Playwright，**最终切换为 Playwright + Python**。这里留下决策依据，方便以后复核。

## 结论

Playwright 更适合作为“可重复、可并行、可留证据”的测试引擎。opencli 的长处（直接借用本人已登录的 Chrome）在本 skill 里用 `wft login --headed` 人工登录一次、保存登录态来替代。

## 对比（含真实环境实测）

| 维度 | opencli | Playwright（本 skill 现用） |
|---|---|---|
| 复用已登录状态 | 直接用本人 Chrome | 登录一次保存登录态；验证码/MFA/单点登录用 `--headed` 人工完成一次 |
| 多执行者并行 | 所有 session 共用同一个 Chrome 的登录态，后登录覆盖先登录，实测互相顶下线 | 每个上下文独立；实测同账号两个独立上下文，第二个登录后第一个仍在线 |
| 文件上传 | 原生 upload 被浏览器拒绝（CDP Not allowed），需要自写注入脚本 | `set_input_files` 原生支持，实测通过 |
| 无人值守/定时/CI | 依赖桌面 Chrome 窗口与扩展 | 无头运行，用本机 Chrome 通道，无需下载浏览器 |
| 后台标签页渲染 | 后台标签页的下拉菜单不渲染，曾导致把“入口存在”误判成“缺失” | 无头页面始终渲染 |
| 证据 | 截图、网络摘要 | 截图 + trace（含每步 DOM 快照）+ 接口响应捕获（`watch`） |
| 可重复回归 | 每次靠 AI 一步步点，慢且耗 token（实测单会话 150～315 次调用） | 用例固化成 JSON，重放不需要 AI |
| 上手 | 已装好扩展的同事零成本 | `pip install -r requirements.txt` |
| 跨平台 | macOS/Linux 为主 | macOS/Linux/Windows 一致 |
| 与 AI agent 的关系 | 与特定工具链绑定较多 | 命令行 + JSON，任何 agent 或人都能用；需要 AI 现场驱动时可用 Playwright MCP |

## 真实环境试跑结果

1. 登录并保存登录态，再带登录态进入目标页：通过。首版登录脚本有“抢跑”缺陷（单页应用先加载再跳登录页），已修复。
2. 无头模式原生上传、创建最小任务、捕获创建接口响应：通过。
3. 同账号两个独立上下文并行登录是否互相顶下线：一次实测未顶下线（短时实验，结论需继续观察）。
4. 用声明式用例跑完一整套（入口、列表字段、必填、上传校验×7、轮次边界×4、冒烟创建）：10 通过、5 失败，失败项与此前人工测试发现的缺陷一致。
5. 试跑中暴露两个自身缺陷（定位到了列表搜索框而误创建数据；异常包被当成正常数据），已修复并加入“数据创建护栏”。

## 其他候选

| 候选 | 评价 |
|---|---|
| Playwright MCP（`@playwright/mcp`） | 适合让 AI agent 现场探索页面；探索出的步骤再固化成 JSON。已实测启动、加载登录态、本地页面完整交互、真实业务页面的校验链路，详见 `08-PlaywrightMCP接入.md` |
| Chrome DevTools MCP | 强在性能/网络/控制台排查，不是回归和并行的首选 |
| Puppeteer | 能力接近，只覆盖 Chromium，生态不如 Playwright |
| Selenium | 老牌，等待与稳定性不如 Playwright |
| Cypress | 偏前端项目内测试，对跨系统黑盒验收不如 Playwright 灵活 |

## 仍然存在的限制

- 只覆盖了用户名密码登录；单点登录/验证码需要人工登录一次保存登录态。
- 登录态文件等同凭据，需要妥善保管、定期重新登录。
- 无头浏览器与真实桌面 Chrome 在字体、下载目录、弹窗上有细微差异，不影响功能判定。
- 公司若限制安装 pip 包，需要提前与 IT 确认。
